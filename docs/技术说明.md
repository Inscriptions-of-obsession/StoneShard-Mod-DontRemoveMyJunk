全量反编译审计列出的三个理论隐患，核实后均关闭：

1. **商队 Spices 0.5 倍率未复刻**：原版对商队系容器（且商队开了 Spices 升级）

   不可销毁（双重所有权风险，见零·六 C），属 delete/clear 语义的结构性代价。
3. **"容器重建偏移随机"不适用于可盗窃容器**：随机偏移只存在于 biome/地牢
   动态生成器（`choose(52,-52)`），那些容器无主、不被记录。可盗窃容器
   （定居点）为 RoomCC 静态摆放/固定种子生成，坐标跨重建固定——日志中
   19 次 `ok1` 全部是坐标命中重建后容器的实证。唯一敞口是游戏内容更新
   改动布局（vanilla 级），由 roomTag 兜底接住（物品不丢）。

## 零·五、坑九：房间编号漂移 → 挂起表孤儿化（v1.8.0 修复）

**症状**：剧情推进（如与维伦对话）后回到村庄，容器已刷新，但存放的物品没有抛出。
再读档回去箱子又没刷新、物品还在——同一容器在两次会话里表现割裂。

**根因**（两次复现 + 日志钉死）：挂起表桶键用 `string(room)`（GameMaker 房间编号），
而房间编号**不稳定**——剧情推进重建地图后同一地点的房间编号漂移
（实测同一容器所在房间 `198 ↔ 224`）。抛出侧按新编号查 `cePending["198"]`，
条目却在 `cePending["224"]` 下 → 静默退出、一条日志都不写，物品成孤儿。

**检测与抛出链路本身从未失手**——45 条历史 eject 日志里该 skip 的 skip、
该抛的抛，无一误判。坏的只有"查表分桶"这一步。

**修复（v1.8.0 换键）**：挂起表改用游戏自身的持久化身份键。

```
cePending[locationTag]["x,y"] = { "roomTag": 字符串, "items": 物品列表 }
```

| 键 | 值 | 稳定性依据 |
|---|---|---|
| 桶键 `locationTag` | `scr_locationGenerateTag()` = 世界坐标格式化（`"locationX_locationY"`） | 游戏自身的门锁/犯罪/preset flags 持久化同款键，跨读档与剧情重建稳定 |
| 条目键 `"<x>,<y>"` | 容器坐标（定位第一键、**决定权**） | 容器坐标被游戏归一化到格子（`scr_round_cell(x) + 13`），重建落同格；实测跨重建命中 |
| 条目值 `roomTag` | `scr_locationRoomGenerateTag()`（第二键、**仅辅助定位**） | 野外 `"r_global"` / 地牢 `"r_dungeon_N"` / 室内 `room_get_name(room)` |

**定位与兜底链**（决定权始终在坐标 + 状态）：

1. 主路径：坐标命中容器 且 `is_execute == false`（状态变更）→ 抛在 `(x,y)`
2. 坐标命中但 `is_execute == true` → **不抛不兜底**（物品还在容器里，抛了就是复制）
3. 坐标失效（键损坏 / 找不到容器实例）且条目 `roomTag` 与当前房间一致 →
   在房间内找"已刷新的可盗窃容器"（`hasOwner` 且 `is_execute == false`）抛在其脚下
   （日志动作列 `ejectfb:` 前缀）
4. 两者都失效 → 不抛出，条目保留等下次（v1.4.0 起"不成功不删"）

**已知边界**：兜底路径（3）无法验证目标容器的状态变更，若房间内存在从未开启的
可盗窃容器可能误配位置——罕见情形的尽力救援，实测如出现再收紧判据。
旧结构（桶键 = room 数字）的条目不再读写，作为历史损失自然废弃。

**顺带载荷加固**：物品列表直接挂进条目（`ds_map_add_list` 自带标记），
不再 `ds_list_clone`——消除副本标记位丢失导致的结构损坏风险（早期 5 次
`ok0` 乱清单的病灶：清单长度 0/1/43、内层类型不符）。

**实测验证清单**（v1.8.0）：日志新增 `loc` / `roomtag` 两列，跑一遍剧情推进复现，
确认两列值跨重建不变；确认 `eject:` 动作出现；确认 `ejectfb:` 仅在坐标失效时出现。

## 零·四、坑七：必须限定"有主容器"

实测发现：一楼容器刷新后，**连箱子里原本就有的发霉食物也被抛了出来**。

原因是判据不严。`HasOwner` 的语义是：

| 值 | 含义 |
|---|---|
| `0` / 无此键 | **玩家存入的普通物品** |
| `0` / 无此键 | **无主容器的原生战利品** ← 与上一行无法区分 |
| `1` | 有主容器首开生成的原生战利品 |
| `2` | 失物 |

`c_container_Other_13` 只在 `if (hasOwner)` 时才给生成的物品打 `HasOwner = 1`：

```gml
is_execute = true
if (hasOwner) {
    with (o_inv_slot) ... scr_inv_atr_set("HasOwner", (1 << 0))
}
```

所以**无主容器的原生战利品 `HasOwner` 也是 0**，和玩家存进去的完全一样。

修法：记录时只认有主容器

```gml
if (instance_exists(_ce_w) && instance_is(_ce_w, c_container)
    && variable_instance_exists(_ce_w, "hasOwner") && _ce_w.hasOwner)
```

这样判据重新变得干净：原生战利品必带 `HasOwner == 1`、失物是 `2`，
只有玩家存入的（`0`）会被记录。这也正是需求所说的"**可盗窃容器**"。

## 零·三、坑六：GML 作用域——`var` 不能声明在 with 所在的作用域里

读档后抛出钩报：

```
Variable o_roomEntityLoader._ce_hit(120047, -2147483648) not set before reading it.
```

GML 中「**循环体内 `var` 声明 + 嵌套 `with` 内对同名变量赋值**」这个组合，
编译器会把该变量判定为 **with 目标实例的实例变量**，而非函数局部变量。
读取时槽位仍是未初始化状态（报错里的 `-2147483648` 就是"未赋值"标记）。

游戏自己的同类代码是反例中的正例 —— `scr_locationRoomEntityContainersInstanceGet`
把变量声明在 `with` **之前**的函数作用域：

```gml
var _array = []
with (o_stuff) { ... array_push(_array, id) }    // 安全
```

**正确写法**：所有变量提升到 `while` 之前、函数作用域内，并显式初始化：

```gml
var _ce_key = ds_map_find_first(_ce_room)
var _ce_hit = noone
var _ce_tx  = 0
...
while (!is_undefined(_ce_key))
{
    _ce_hit = noone
    with (o_stuff) { ... _ce_hit = id }   // 赋给外层局部变量
}
```

记录钩（`ce_record.gml`）没有 `with` 赋值，不受此影响，保持原样。

## 零·二、坑五：`scr_loot_drop_saved` 的参数顺序

```gml
function scr_loot_drop_saved(argument0, argument1)   // argument0 = 布尔开关
{
    if (argument0 == undefined) argument0 = false
    if (argument1 == undefined) argument1 = -4
    if (argument1 == -4) argument1 = loot_list        // ← 省略时兜底成当前容器的 loot_list
```

写成 `scr_loot_drop_saved(_ce_items)` 会把待抛列表落到 `argument0`（布尔位），
`argument1` 保持 undefined → **兜底成容器自己的 `loot_list`**。
而刚被刷新的容器 `loot_list` 是空的，循环跑 0 次，
表现为"日志显示 eject、但地上什么都没有"。

正确写法：

```gml
with (_ce_hit)
    scr_loot_drop_saved(false, _ce_items)
```

## 一、功能

紫色晶石每七天会按 `presetTag` 世代更替，使地图上所有容器存档失效，
玩家存放在可盗窃容器里的**自有物品**会随之消失。

本模组把这些物品记录下来（挂起表），当玩家再次进入该区域、
且确认容器确实已被刷新重建时，把它们抛回容器脚下。

失物（`HasOwner == 1` 或 `2`）**不计入**挂起表，刷新时随原战利品一起消失。

## 二、核心机制

### 失物判定：看标记，不看来源

游戏从不记录"这件物品原本属于谁"，只在物品的 `data` map 上贴 `HasOwner` 标签：

| 值 | 含义 | 设置位置 |
|---|---|---|
| `0` / 无此键 | 普通物品 | `o_loot_Create_0` |
| `1` | 从有主容器首开生成 | `c_container_Other_13` |
| `2` | 失物 | `scr_inv_find_free_cell` |

标记存在 `data` 里，而 `scr_save_item_single` 做的是 `ds_map_clone(data)`，
所以标记能完整穿越存档往返。本模组据此把 `HasOwner` 为 0 的物品判定为玩家自有。

### 刷新判定：`is_execute`

`is_execute` 是容器的"是否已被搜刮"标志：

- 玩家存放过物品 → 必然被搜刮过 → `is_execute == true`
- 七天世代更替后重建的实例从未被搜刮 → `is_execute == false`

所以 `is_execute == false` 即表示旧世代数据已失效、记录中的物品确实已消失，
此时才抛出。未满七天就返回的情况 `is_execute` 仍为 true，物品还在箱内，不抛，
记录保留等待日后真正的刷新。

### 挂起表（模组自有，不属于游戏本体）

```gml
// v1.8.0 结构（旧版桶键是 room 数字，剧情重建后漂移，已废弃）
global.saveDataMap["cePending"] = {
    "<locationTag>": {                        // 桶键 = scr_locationGenerateTag()（世界坐标）
        "<x>,<y>": {                          // 键 = 容器坐标（定位第一键、决定权）
            "roomTag": "<roomTag>",           // 第二键、仅辅助定位（兜底用）
            "items": [ 物品数组, ... ]
        }
    }
}
```

**必须经由 `global.saveDataMap` 访问，不要缓存到独立全局变量。**

游戏自己的 `scr_containersLootMapInit()` 就是证据：

```gml
function scr_containersLootMapInit() {
    if global.is_load_game
        global.containersLootDataMap = ds_map_find_value(global.saveDataMap, "containersLootDataMap")
    else { ... ds_map_add_map(global.saveDataMap, "containersLootDataMap", ...) }
}
```

读档后游戏**必须主动把全局变量重新绑定到 saveDataMap 里的嵌套 map**，
说明 `saveDataMap` 在读档时会被整体替换/重填。

若把挂起表缓存成 `global.cePending`，读档后它仍指向**已被丢弃的旧 map**：

- 后续写入进了一个游戏根本不会序列化的孤儿 map → 该存档不丢东西，但换档后数据错乱
- 更糟的是旧 map 可能已被销毁 → 访问即崩

挂在 `saveDataMap` 下面则**天然随存档序列化、随读档还原**，
既不需要生命周期钩子，也不会出现指针失效。
每个访问点都是：

```gml
var _ce_pending = ds_map_find_value_ext(global.saveDataMap, "cePending", -1)
if (_ce_pending == -1) {
    _ce_pending = ds_map_create()
    ds_map_add_map(global.saveDataMap, "cePending", _ce_pending)
}
```

这同时满足了"存档时记录挂起表匹配存档、读档时以该存档的挂起表为准"的要求：
存档那一刻 `saveDataMap` 里是什么，存进去的就是什么；读档时整个 `saveDataMap`
被换成存档里的版本，挂起表自然随之还原。

> 唯一保留的全局变量是 `global.ceScratch`（记录时的临时快照缓冲），
> 它不参与持久化，每次使用前 `ds_list_clear`，跨存档残留无害。

## 四、重要坑：`Alarm_0` 无法被 MSL 注入

最初把记录钩选在 `o_container_parent` / **Alarm 0**（`scr_save_item` 那一行之后），
实测直接失败：

```
GML Compile Error: Expected assignment operator around line 112, column 9.
```

逐行二分定位到根因：该函数内含 **`self.update_ammo_order()`** 方法调用，
而 UndertaleModLib 的 GML 解析器**无法处理 `self.xxx()` 方法调用语法**，
整段函数重编译必然失败——MSL 对这个函数注入任何内容都会抛异常。
`gml_GlobalScript_scr_save_item` 同样不可编译。

已实测可编译的候选锚点：

| 代码 | 可注入 |
|---|---|
| `o_container_parent_Other_23` / `Other_25` / `Step_2` / `Destroy_0` / `Create_0` | ✅ |
| `o_roomEntityLoader_Other_11` | ✅ |
| `c_container_Other_13` / `Other_15` | ✅ |
| **`o_container_parent_Alarm_0`** | ❌ 含方法调用 |
| **`gml_GlobalScript_scr_save_item`** | ❌ |

**后续在这个项目里注入前，先确认目标函数能通过 UTMT 重编译。**

### 坑二：`[]` 是数组，不是 ds_list

GML 中 `var x = []` 创建的是**数组**，而 `ds_list_add` / `ds_list_size` /
`ds_list_clone` 全部只接受 ds_list，混用会抛：

```
ds_list_size argument 1 incorrect type (array) expecting a Number (YYGI32)
```

首版 `ce_record.gml` 用 `var _ce_keep = []` 存待挂起物品、
`ce_eject.gml` 用 `var _ce_done = []` 存待清理键，都是这个问题。

**它只在空箱子时暴露**：容器为空时遍历循环跑 0 次，`ds_list_add` 没被调到，
错误推迟到下一句 `ds_list_size` 才抛出；容器非空则在 `ds_list_add` 处先炸。
两种情况都是致命的，只是报错行不同 —— 容易误判为"只有空箱子才有问题"。

已全部改为 `ds_list_create()`。真正需要数组的地方只有
`string_split()` 的返回值，那里配 `array_length()` 是对的。

### 坑三：不要用内置 `string_split()` 的返回值做 `[]` 索引

本作 GML 环境里内置 `string_split()` 的返回类型不可靠，对它用 `[]`
会抛 `trying to index a variable which is not an array`（实测发生）。

游戏本体内部大量使用的是**自有的 `string_split_custom()`**，那个才是确定返回数组的：

```
scr_stringCapitalize :  var _stringArray = string_split_custom(argument0)
                        var _stringArrayLength = array_length(_stringArray)
scr_loot_from_tables :  _item_tier = string_split_custom(_item_tier, ",")   ← 全部用它
```

内置 `string_split` 也有数组式用法（`scr_dungeonFloorSeedGenerate` 等），
但返回值类型无法静态确定，**不要依赖它**。

键格式固定为 `"<x>,<y>"`，因此本模组直接用无歧义的字符串函数解析：

```gml
var _ce_comma = string_pos(",", _ce_key)
var _ce_tx = real(string_copy(_ce_key, 1, _ce_comma - 1))
var _ce_ty = real(string_copy(_ce_key, _ce_comma + 1, string_length(_ce_key) - _ce_comma))
```

同时把 `_ce_done[_ce_i]` 也换成了 `ds_list_find_value(_ce_done, _ce_i)`，
整个模组现在**零 `[]` 索引**。

### 坑四：函数必须能在 data.win 的注册表里查到

误用 `string_find`（想当然以为存在）导致启动即崩：

```
Error on load
Unable to find function string_find
```

已改用 `string_pos`（游戏本体大量使用的经典函数）。

同时补了一个静态校验器，逐个文件提取所有被调用的函数名，
对照 `data.Functions`（7466 个内置）+ `data.Scripts`（10042 个脚本）核验：

```
内置函数 7466，脚本函数 10042，合并后 10752
✅ Container Eject\re-source\Codes\ce_eject.gml
✅ Container Eject\re-source\Codes\ce_record.gml
✅ Talk Ender\re-source\Codes\esc_last_option.gml
```

**以后新增/修改 GML 后应先跑一遍这个校验再打包。**
注意校验器不剥离字符串字面量，像 `recipe(s)` 这种日志文本会被误报，需人工排除。

### 调试日志格式（v1.6.2 起为 10 列）

```
time,stage,room,container,snapshot,kept,ids,now,fresh:stamp,why
time,stage=record,room,"x,y",<箱内物品总数>,<判为普通物品数>,<留下的物品名/…>,<当前游戏分钟>,<Fresh:Timestamp>/…:st<N>,（空）
time,stage=eject ,room,"x,y",<待抛数>,<动作>,<实际交给抛出函数的物品名/…>,<当前游戏分钟>,<Fresh:Timestamp>/…,<why字段>
```

**`why` 列（v1.6.2 新增）**：只在校验阶段有物品被拒时出现，
格式 `why<槽位序号>=<失败项>|<槽0类型>|<长度>|<槽1类型>|<槽0值类型>/`

| 失败项 | 含义 |
|---|---|
| `0` | 槽 0（物品数组本身）不是 ds_list |
| `1` | 长度不足 2 |
| `2` | 槽 1（数据 map）不是 ds_map |
| `3` | 槽 0 的值（`[0]` 物品名）既不是字符串也不是数字 |

类型码：`str` 字符串 / `arr` 数组 / `list` ds列表 / `map` ds映射 / `num` 数字 / `?` 都不是（可能是 undefined）

例：`why0=2|list|10|arr|-/-` → 物品数组本身完好（长度 10），但 `[1]` 是数组不是 map。

其它列含义：

`ids` 列用来确认"记的是什么"和"抛的是什么"。
`now` 是 `scr_timeGetTimestamp()`（游戏内总分钟）；
`fresh:stamp` 是每件物品的 `Fresh` / `Timestamp` 属性对（不存在则记 -4），
记录行末尾 `:st<N>` = 本次补戳件数。

**`fresh` 列同时是一个量纲测量器**：开过的容器里游戏自己会扣 `Fresh`，
所以同一只箱子关箱两次之后

```
真实腐败速率 = (Fresh₁ − Fresh₂) / (now₂ − now₁)
```

单位就这么直接测出来，不用靠猜。

### 日志轮转（v1.7.1）

`ce_debug.csv` 超过 **1000 行**时自动清空重建、补回表头，然后继续写入后续条目，
不需要手动删文件，长期挂着也不会无限膨胀。

两侧（记录侧 `ce_record.gml` / 抛出侧 `ce_eject.gml`）同一套规则：

1. 开句柄**之前**先用 `file_text_open_read` 逐行读出来数，行数存进 `_ce_lines`；
   文件不存在时句柄为 `-1`，`_ce_lines` 保持 0，等价于"新文件"。
2. `_ce_lines > 1000` → 先关掉刚开的 append 句柄，再用 `file_text_open_write`
   重新打开（截断清空），并把 `_ce_lines` 置 0。
3. `_ce_lines == 0` → 补写一次表头。

**轮转判定必须放在开句柄之前**，因为抛出侧的句柄要跨整个 `while` 循环保持打开
（一次房间载入可能写多行），循环里只负责往开着的句柄写。

> 顺带修掉一个旧写法：v1.7.1 之前两侧都用 `file_exists` 判断"要不要写表头"，
> 但 `file_text_open_append` 会**先把文件建出来**，之后 `file_exists` 恒为真——
> 只要日志文件曾经存在过，表头就再也不会补上，新文件第一行会是空的。
> 现统一改为按"行数为 0"判定。

轮转不影响任何游戏行为，纯粹是调试文件的自我管理。

### 食物保质期：量纲实测（v1.6.0 的依据）

同一只箱子关箱两次，日志给出：

```
86604,record,131,546,286,3,1,o_inv_pancakes/,17659,120:17642/
99004,record,131,546,286,3,1,o_inv_pancakes/,17731,119:17731/
```

`now` 走了 **72 游戏分钟**，`Fresh` 只掉 **1**；物品自身 `Timestamp` 的更新间隔是 89 分钟，
`floor(89/60) = 1`，与 Fresh 跌幅精确吻合。

> **结论：`Fresh` 以【游戏小时】为单位，每次扣减 = 经过的整小时数。**
> 代码对应 `scr_timeGetPassed(Timestamp, 2)`（参数 2 = 小时，3 = 天，4 = 月）。

`Fresh = 120` 即 120 游戏小时 = 5 游戏天，对食物来说很合理。

**实现要点（三个都踩过）：**

1. 挂起表里没有活实例，没人跑 `o_inv_food_parent` 的 `alarm[8]`，
   必须在交给 `scr_loot_drop_saved` 之前按绝对时间补扣。
2. **光把 `Fresh` 归零不够，必须换物品名。**
   游戏里"变成腐坏食物"是运行时换对象、由 `can_change` 门控，
   而 `o_inv_food_parent` 的 Create 只在 `roomEntityTag == "drop"` 时置 `can_change = true`。
   抛出的实例 Create 跑在 `scr_loot_drop` 打完标签之前，`can_change` 恒为 false，
   结果会是一个 `Fresh = 0` 却看起来完好、永远不变腐的食物。
   所以过期时要 `ds_list_set(_item, 0, asset_get_index(<名字> + "_rot"))`。
3. **`asset_get_index` 不是 `__asset_get_index`。**
   反编译出来的游戏代码写的是 `__asset_get_index`，但那只是反编译器对 opcode 的渲染；
   data.win 里真正的内置函数名是 `asset_get_index`
   （`__asset_get_index` 只以 `gml_Script___asset_get_index` 这个脚本壳存在）。
   GML 源码必须写 `asset_get_index`，否则静态校验器会报未确认函数。
4. 没有 `Timestamp` 的物品（合成/购买后直接进箱、从未当过地面掉落物）
   **在关箱那一刻补一个基准**（v1.6.1 修正）。
   v1.6.0 原写的是"一律不动"，那会把这类食物永久冻结——而实测证明
   **箱子里生成的食物只要箱子被打开过，游戏的腐坏计时是会启动的**，
   并不是永远不会计时。所以必须从关箱那一刻起让游戏内时间对它生效。
   这个修改只作用于快照内的 data map（`scr_save_item` 内部 `ds_map_clone`
   出来的副本），不影响容器自己的 `loot_list`。

日志动作列末尾新增 `:rot<N>`，N = 本次被换成 `_rot` 变体的件数；
记录行 `fresh:stamp` 末尾的 `:st<N>` = 本次补戳件数。

## 六、已知限制与待实测项

1. **进房间时序依赖 `o_roomEntityLoader`**。若玩家在该钩执行前就打开容器，
   `is_execute` 会变 true，判定失效、物品永久丢失。需实测确认这个窗口不存在。
2. **消费者容器未处理。** `o_inv_consum` / `o_weapon_loot` 走的是
   `data["lootList"]` 而非 `loot_list`，本模组只处理 `c_container` 分支。
3. **物品身份比较依赖 `HasOwner`**。玩家把**自己偷来的失物**放进容器时，
   该物品带标记，不会被记入挂起表，刷新时会被丢弃。这是需求明确要求的行为。
4. **挂起表只增不减**：玩家存入后既不取回也不再访问的区域，其记录会长期留存。
5. **存档/读档**：v1.4.0 已补上 `ds_list_mark_as_list`（见坑九），
   并在抛出侧加了类型防御，实测崩溃已消除。但**旧存档里被写坏的条目无法恢复**——
   防御只会跳过它们。需要用 v1.4.0 重新在容器里存一次物品，让记录以正确格式重建。
6. **"抛出的物品与预期不符"（二楼只出现绳子）尚未定位**。
   v1.4.0 的日志新增 `ids` 列，会记录实际记录/抛出的物品名，
   拿到新日志即可区分是"挂起表里存错了物品"还是"抛对了但落地位置/对象不对"。
7. **E：scr_loot_drop_saved 存在理论上的静默失败路径（v1.8.1 核对后判定不修）。**
   该函数不返回成败、失败不报错，模组以"调用完成"当作"交付成功"并删除条目。
   三条理论失败路径及其关闭理由：
   - 丢法1（普通物品的 `o_loot_*` 地面对象不存在）：本体物品全部配有掉落物版本
     （玩家 Q 键丢弃走同一翻译路径，缺版本的 mod 物品连"扔地上"都是坏的，
     机制强迫 mod 作者做对）→ 概率≈0。
   - 丢法2（武器 idName 不在 `global.weapons_stat` 注册表）：玩家亲手存入的
     武器必然在拾取/购买时已注册 → 正常游玩不可能触发。
   - 丢法3（idName 撞非物品资产名，被解析成错误对象走错分支）：vanilla 反证——
     游戏自己砸容器（`c_container_Destroy_0`）走同一条函数，多年无"砸容器
     武器消失"报告；且多数 idName 带 `" notId"` 后缀（含空格），GMS 资产名
     不含空格，`asset_get_index` 必然查不中，天然免疫撞名。
   原版的防呆在**读回路径**（`scr_loadContainerContent` 的
   `object_is_ancestor` 检查 + idName 重建），防的是游戏更新后的资产索引漂移；
   掉落路径（本模组所用）无防呆但也被上述三点覆盖。
   剩余敞口仅"游戏大更新导致旧档资产索引漂移"——vanilla 级问题，对账也救不了。
   后果若发生：物品永久消失且零日志（症状同坑五"日志成功、地上没有"）。
   曾考虑对账方案（调用前后数掉落物增量），因三条路径概率均≈0、对账复杂度
   与误判风险（需按 data.idName 分组对账）不匹配收益，判定不修。
8. **部分容器子类开箱不打 `HasOwner=1`（原生战利品可能被误记）。**
   `o_abbeybarrels01` / `o_lootcrate1` 的 Other_13 与 `c_container_Other_13`
   不同：只置 `is_execute = true`，没有 `if (hasOwner)` 打标段
   （`c_abstract_chest` 走 `alarm[1]` 延迟生成，本家族打标情况静态不可查——
   反编译不含对象父子元数据）。若这类容器以 `hasOwner == true`（玩家领地）
   存在且玩家往里存物品：原生战利品（`HasOwner == 0`）会被当成玩家物品记入
   挂起表，刷新后随玩家物品一起抛出——后果是**多得一份免费原生战利品**
   （复制收益，方向与丢失相反，非物品损失）。
   **概率评估（v1.8.1 核对后进一步收敛）**：`reputation`（hasOwner 的数据源）
   全项目唯一写入点是 `o_globalmap_settlement`（大地图定居点对象初始化）——
   只有定居点世界格上的容器才 hasOwner=true。战利品箱（硬编码战利品的
   开箱即取设计）与修道院木桶大概率不在定居点格子上 → 无主 → 被 record 侧
   第一道门（`_ce_w.hasOwner`）直接过滤，**缺陷在模组适用范围内不存在**。
   原版自洽性佐证：打标条件 `if (hasOwner)` 本身宣告"无主容器无需打标"
   （HasOwner 的消费方是犯罪/所有权系统，只管有主领地）——打标范围与
   本模组的记录范围以同一个 hasOwner 收口，两边对齐。
   触发还需：玩家反常地往战利品桶里存自己的东西且不拿原生战利品 + 七天刷新。
   模组 14 个版本、45+ 条记录日志、实测"没漏没多"，无一次触发迹象。
   判定不修，记录在案。修道院木桶的 hasOwner 若需实测：在修道院对任意木桶
   存一件物品关箱，看日志是否出现 record 行即可判定。
9. **"砸毁容器后刷新 = 复制"已排除（v1.8.1 核对后判定不成立）。**
   理论链路：砸毁容器（Destroy_0 掉出 loot_list，含玩家物品）→ 条目未撤销 →
   刷新后模组再抛一份 = 复制。但源码证实可盗窃容器**不可摧毁**：
   `c_container_Create_0` 仅 `event_inherited()`，can_broke 继承基类
   `o_abstract_stuff_Create_0` 的 `false`；全项目房间实例创建代码（RoomCC）
   零处 `can_broke = true`；can_broke = true 的容器类（`c_dungeon_table`、
   `o_bastonfoodbarrels` 等）全部位于地牢/野外（无 reputation）→ hasOwner
   = false → 本模组不记录。即"可摧毁"与"有主"两个集合在实践中不相交
   （同一所有权边界同时约束原版的可摧毁性与本模组的记录范围），
   链条第一步（砸毁可盗窃容器）不存在。

## 七·一、GML 静态校验器

本项目连续三次因函数/类型用错而崩溃，因此固化了校验工具：

```powershell
dotnet run --project "D:\Trae program\Tools\Analysis\ValidateGml" -- "D:\Trae program\某个模组"
```

它会把该目录下所有 `re-source` 的 `.gml` 里被调用的函数名逐个对照
data.win 的 `Functions`（7465 个内置）+ `Scripts`（10042 个脚本）核验，
输出未确认的函数名。**改完 GML 先跑它再打包。**

局限：不剥离字符串字面量，英文日志里的 `recipe(s)` 这类会误报，需人工排除。

## 七·二、GML 反编译导出器（DumpGml）

排查"抛出执行了却没东西"需要反复读游戏本体代码，因此固化了一个导出器：

```powershell
dotnet run --project "D:\Trae program\Tools\Analysis\DumpGml" -- "<输出目录>" [名称过滤...]
```

不传过滤则导出全部脚本与对象事件。名称按 data.win 原名匹配（子串、忽略大小写）：

```powershell
# 精确导出某个函数
dotnet run --project "...DumpGml" -- dump scr_loot_drop_saved
# 导出某个对象的所有事件
dotnet run --project "...DumpGml" -- dump o_container_parent c_container
```

输出为 UTF-8 无 BOM + LF 的 `.gml`。data.win 里存在 >260 字符的嵌套匿名脚本名，
直接当文件名会抛 `IOException`，导出器已对超长名截断并追加哈希后缀。

注意：本 UTMT 版本的 API 与网上常见示例不同 —— 是 `data.GameObjects`（不是 `data.Objects`）、
`GlobalDecompileContext(data, enableStringLabels)`、`Decompiler.Decompile(code, ctx)`，
对象事件要遍历 `o.Events`（外层是事件序号、内层才是事件）的 `ev.Actions[].CodeId`。

## 七·三、坑八：掉落物被建在了错误的图层（v1.3.0 修复）

**症状**：调试日志明确显示 `eject:ll0:ok3/3`——三个物品全部通过结构校验、
`scr_loot_drop_saved` 也确实被调用了，**但地面上什么都没有，且不报任何错**。

**根因**：`scr_loot_drop_saved → scr_loot → scr_loot_drop` 的最后一步是

```gml
_instance = instance_create_depth(argument0, argument1, 0, argument2)
```

GameMaker 的 `instance_create_depth` 把实例建在**调用者所在的图层**上。
抛出钩挂在 `o_roomEntityLoader`（实体图层），于是掉出来的 `o_loot_*` 物品
被建在实体图层上：既不在地面掉落物图层（看不见），也不与玩家碰撞（捡不到）。
整条链路没有任何断言会失败，所以表现为"静默无效"。

**修复**：把调用包进 `with (o_player)`，玩家所在图层正是地面掉落物所在的图层；
位置用临时改写 `x` / `y` 的方式指到容器坐标，调用完立刻改回：

```gml
if (instance_exists(o_player)) {
    with (o_player) {
        _ce_px = x
        _ce_py = y
        x = _ce_tx
        y = _ce_ty
        scr_loot_drop_saved(false, _ce_valid)
        x = _ce_px
        y = _ce_py
    }
} else {
    with (_ce_hit)          // 极端兜底
        scr_loot_drop_saved(false, _ce_valid)
}
```

**教训**：调用游戏"生成世界实体"这类函数时，**`self` 所在的图层本身就是输入的一部分**。
从非世界对象（加载器、GUI）里调用会把实体生到错误的图层去，而且不报错。
判断某段代码"从模块里调用是否安全"，不能只看参数，要看 `self` 上下文。

### 坑九：`ds_list_add` 之后不标记，存档往返后嵌套结构会退化成字符串（v1.4.0 修复）

**症状**：存一次档再读档后，进房间直接崩：

```
ERROR in
action number 1
of Other Event: User Defined 1
for object o_roomEntityLoader:

ds_exists argument 1 incorrect type (string) expecting a Number (YYGI32)
at gml_Object_o_roomEntityLoader_Other_11
```

**根因**：游戏的存档链路就是整棵 `saveDataMap` 的 JSON 往返：

```gml
// scr_dsMapSave
var _mapStringHash = scr_stringHashSave(json_encode(argument2), argument3)
// scr_dsMapLoad
_map = json_decode(_mapString)
```

GameMaker 的 `json_encode` **只有在嵌套槽位被标记过**时才输出嵌套的数组/对象；
未标记的 ds 引用会被写成标量字符串。而 GameMaker 的 ds 句柄本身是 real，
读回来就是一个字符串，`ds_exists(字符串, ...)` 当场抛错。

游戏本体处处都在标，本模组此前一处都没标：

```gml
// scr_save_item 末尾
for (var i = 0; i < _list_size; i++)
    ds_list_mark_as_list(argument0, i)

// scr_save_item_single
ds_list_mark_as_map(_item, ds_list_size(_item) - 9)   // 物品的数据 map

// scr_locationRoomEntityStaticSave
ds_list_add(_entityTagList, _entityDataMap)
ds_list_mark_as_map(_entityTagList, ds_list_size(_entityTagList) - 1)
```

我们此前用裸 `ds_list_add` 把物品塞进 `_ce_keep`，于是存档时整个物品数组变成字符串。

**只有 `ds_list_add` 需要显式标记**：`ds_map_add_map` / `ds_map_add_list` 自带标记。
`ds_map_mark_as_map` / `ds_map_mark_as_list` 在本作 GameMaker 版本里**根本不存在**
（校验器会报未确认函数；游戏本体全项目零处使用），别去调。

**修复与兜底**（v1.4.0 做了三件事）：

1. `ce_record.gml` 里补上 `ds_list_mark_as_list(_ce_keep, ds_list_size(_ce_keep) - 1)`
2. `ce_eject.gml` 对每个 `ds_exists` 加类型防御。判据只能是
   `!is_string(x) && !is_array(x)`——**不能用 `is_real` 排除，因为 ds 句柄本身就是 real**。
   这样存档里残留旧版写坏的条目也只会跳过，不会让游戏崩溃。
3. **一件都没抛成功时不再删除挂起条目**。以前无论成功与否都删，
   结构一坏等于物品被静默销毁；现在只有真正交出去才删，其余保留以便重试。
